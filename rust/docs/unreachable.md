# Unreachable differences

Differences between C# and Rust that need a forged id, a null the client can't send, a broken game state, or execution of an event that never passed validation (PORTING.md, "Scope"). They are not investigated or fixed. One line each.

- `SetIncreasedRevivalLimits` with `Factions` null, executed without validation: C# stores null in `Game.FactionsWithIncreasedRevivalLimits` (live fuzz seed 61 game 5, seed 9311 games 0 and 43; [pkg-f review](reviews/pkg-f.md) item 1, pkg-k item 4). Rust now matches anyway: the field is an `Option`.
- Undo replay where an event keeps the old game's `Player` because its initiator isn't seated in the replayed game, and the "third game" lookups that follow from it: a validated history replays with the same players, so this needs an event that changed state and then threw (`EstablishPlayers` seating players before an exception, fuzz-2026-00084). Rust models it anyway (`undo_identity.rs::replayed_event_keeps_the_old_games_player`, `event_of_another_game_with_a_player_of_this_game`).
- `DealOffered.Same` with a null `To` (needs a forged `"To":null`): C# 14 binds `To.SequenceEqual` to `MemoryExtensions`, so null equals `[]`. Package K review item 1. Rust matches anyway (`deal_offered.rs`); [span-binding.md](span-binding.md) lists every span-bound call, and none differs on a non-null array.
- `EstablishPlayers` "Cannot draw from an empty deck", C# phase `execute`, Rust `validate` (package K review, fuzz seed 9311, 6 games): needs settings that `Validate` rejects from version 170 (more seats than factions, or more seated players than seats), or a second EstablishPlayers mid-game. It no longer reproduces with the current fuzzer (seed 9311: 48 of 48 pass), and an unvalidated mid-game EstablishPlayers at v176 and a validated one at v103 behave the same in both engines.
- `Revival` with an initiator that has no player (`"Initiator":0`), executed without validation (fuzz seed 37 games 16 and 22): `Player` is null. C# passes it to `PlayNexusCard`, which stones `NexusPlayed` before its first member access throws. Rust throws at `let me = self.player()` at the top of `execute_concrete_event`, so `RecentMilestones` is one shorter. Other `execute_concrete_event` bodies that read `self.player()` up front behave the same way when `Player` is null.
- `PerformHmsMovement` to the HMS itself, executed without validation (fuzz seed 41 game 2 with the short-lived unvalidated-steps fuzzer): the HMS gets attached to itself, and `AttachedLocation.Sector` recurses until the C# stack overflows, which kills the oracle process. Validation rejects the move.
- Server, `string.ToLower()` on letters added in Unicode 16 and 17 (U+1C89, U+A7CB to U+A7DC, Garay U+10D50 to U+10D65, Beria Erfe U+16EA0 to U+16EB8): C# leaves them unchanged with this machine's ICU, Rust lowercases them (`server/src/dotnet_string.rs`). The deployed server's ICU version decides what C# does there; only user names in those scripts would notice. `tests/auth_dotnet.rs` allows exactly these code points.
- Server, a lone UTF-16 surrogate in an e-mail address or user name: C#'s `MailAddress` throws `FormatException` (after the user is saved), while the Rust transport rejects the JSON before the call. A browser text field doesn't produce one.
- Server, `ErrorDetails` of an event whose `Execute` throws (fuzz trace `fuzz-2026-00020`, `SkillAssigned` with leader id -2, through the generated server scenarios): C# returns the engine's "Game Error" message, whose `Technical description` is `Exception.ToString()` with the .NET stack trace and source paths; Rust has no stack trace to print. Only forged ids or engine bugs reach it. Generated server scenarios drop trace steps that recorded an exception.
